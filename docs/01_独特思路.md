# 独特思路

这四点里，前两点是"没人这么做过/公开资料里没有"的部分，后两点是别人普遍做错、
我们做对的部分。

## 一、锚点：玩家自己的落指，取的是**内核时间戳**

**问题**：音游要开打，先得知道"谱面时间 0 对应现实中哪一刻"。这个游戏的谱面文件里
没有前摇时长，加载时间又不固定。同一天同一套逻辑实测标定值：**2.12s / 9.53s /
10.05s / 11.52s**——最大差 9 秒。

**常见做法**：

* 画面检测"演奏画面出现"再减一个常数 → 视频链路有 25~40ms 延迟且会误检；
* 看屏幕上的音符反推偏移（闭环） → 误检一次就把排程推偏几百毫秒；
* 读游戏音频播放位置 → 能读到的计数器每 5 秒才更新，第一个音符早过去了。

**我们的做法**：把**玩家按下第一个音符那一下的内核时间戳**当作 `t1`，
其余音符排到 `F + (t_n − t_1)`。

为什么这是对的：

* 那一下是**游戏刚刚判定接受**的一次音符时刻，等于直接抄了游戏自己的时间轴；
* 用的是**内核时间戳**，所以 adb 读取慢只会延迟"我们什么时候开始发指令"，
  不会让落点偏；
* 玩家的手指和脚本的注入走**同一条输入链路**，链路里的固定延迟自动抵消。

代价：残留误差 = 玩家第一下的时序误差（几十毫秒）。对慢音符无影响，
对 4000px/s 的快滑条会被放大（50ms × 4000px/s ≈ 200px），这也是后面要做
"连续跟随"的原因。

## 二、注入：非 root 的 UHID 虚拟触摸屏

**问题**：现代原厂安卓上，写 `/dev/input/eventN` 被 SELinux 拒绝；
`adb shell input` 每次新起进程 60~80ms、只能单指。

**做法**：借 scrcpy-server 的 UHID 支持，把一份**多点触摸屏的 HID 报告描述符**
交给内核，让系统凭空造出一块真实 HID 数字化仪（`TOUCH | TOUCH_MT`）。
游戏无法区分。

要点：

* 描述符 Logical Maximum 用**面板自然方向（竖屏）**尺寸，否则坐标被缩放；
* 横屏坐标 → HID 坐标是 `(面板宽 − y, x)`；
* scrcpy 必须 `tunnel_forward=true`，服务器起来后要等约 2 秒再连，
  且用随机 scid 避免残留进程抢占。

## 三、谱面驱动，而不是视觉

画面只做一件事：认「乐队确认页」（LIVE START 按钮模板匹配，顺便拿到比写死坐标
更准的按钮位置）。音符的时刻、轨道、类型全部来自谱面数据。

好处：精确、便宜、不会漂。早期版本用视频流识别音符，正是它导致"越打越偏"。

## 四、长条会动，尾巴会甩

把 340 张谱面全解析后的统计：

| 事实 | 数量 |
| --- | --- |
| 音符总数 | 95190 |
| 长条 | 23073 |
| 头尾位置不同的长条 | 11986 |
| 中途会移动的长条（含滑出去又滑回来） | 15311 |
| 尾巴是轻扫的长条 | 2512（上 1536 / 左 492 / 右 484） |
| 头部是轻扫的长条 | 200 |
| 独立轻扫音符 | 6698（只有上/左/右） |

长条横移速度：中位 **1258 px/s**，90 分位 **4346 px/s**。

两个具体结论：

* **每个谱面节点动一次是不够的**（约 157ms 一步 → 单步中位 197px，和音符条容差同量级，
  手指一半时间在条外 → 间歇性 miss）。改成按**位移**重采样（每约 50px 一步、
  同一手指最快 40Hz），单步中位降到 **72px**。
* **尾巴是轻扫的长条**必须三步做完：贴到尾巴位置 → 划出去 → 松手。
