# 独特思路：把"要标定的东西"变成"要算的东西"

> English abstract: the project's core idea is to *derive* the playfield geometry from the game's own
> scene data instead of measuring it, and to use the player's first tap as a **clock** instead of a
> calibration reference. Everything else follows from those two decisions.

## 1. 起点：一个不想猜的锚点

传统做法是"点完开始键 → 等 N 秒 → 开打"，但谱面里没有前摇时长、加载时间也不固定
（同一套逻辑实测标定值在 2.12s / 9.53s / 10.05s / 11.52s 之间跳，差 9 秒，够让整首全 miss）。

于是换成一个不用猜的办法：**你按下的第 1 个音符，就是游戏刚刚判定接受的一次谱面时刻。**
拿那条触摸事件的**内核时间戳**当 0 点，等于直接抄游戏自己的时间轴。

## 2. 代价：从"手按一下"到"位置怎么来"

人手锚点只解决了时间，位置还得有来源。我们走过三条路：

1. **从画面量**（判定线 y、扇形斜率、轨距）—— 走通过，但**每一步都在给自己埋雷**：
   量到的是"看起来像边界的那条线"，不是"第 0 格到第 24 格的宽度"；
   校验用的样本只有一个音符、还在场地中间，误差预算和待测量同量级，
   于是"每次都验证通过"却始终有 40 px 量级的系统偏差。
2. **每台机器存一份档案**（多机型 profile）—— 把不确定性搬家，没有消掉。
3. **从游戏自己的数据算**（最终选的）—— 见下。

## 3. 转折：几何本来就在游戏数据里

演奏区不是一个"随便摆的 UI"，它是游戏自己用常量搭出来的：

| 量 | 出处（游戏函数 / 场景节点） |
|---|---|
| 判定平面 y = −3.16 | `LiveBootDataCreator.CreateViewData` → `LiveSettingCreator.CreateLaneViewSettings`（`judgementScreenBottomPosition = 2.24`，平面半高 ±5.4） |
| 24 格布局、格距 0.64237 | `JudgementPositionLogic.GetJudgementPositions`；`LiveDataCreator.CreateBootData` 传 0x18 = 24 |
| 车道相机 fov = 54°、判定平面在相机前 10.6078 | 场景 `LiveGameView/LiveGameCamera`（Camera 组件 + `screen_root.z`） |
| 6 主线 + 12 副线 → 12 条车道 | `LiveLaneLineView._settings` + `_splitCountType = 2` |

最关键的一条：**判定平面所在距离处的视锥半高 5.4048 正好等于平面半高 5.4**
—— 也就是说平面高度 1:1 铺在屏幕高度上，横向多出来的宽度只是留白。
（另一路佐证：`Live/LiveMainCamera` 是正交相机，`size` 也正好是 5.4。）

于是"跨设备适配"从一个标定问题变成了一个乘法：

```
1 平面单位 = 屏高 H / 10.8 像素
```

## 4. 顺带解决的两件事

* **横屏正反（A/B）消失了**：手指只提供时间戳，坐标方向不再参与任何计算。
* **手指那侧的坐标单位消失了**：不读你的坐标，自然不用管它是 100 还是 16。

## 5. 结果

* 位置：**零标定**，换手机/换分辨率自动正确；
* 时间：你按一下，之后全部由程序按谱面推；
* 运行时不看画面（只在开头认一次确认页），没有 CV 误检的风险。

## 6. 代价（诚实写出来）

* 需要你按一下第 1 个音符 —— 这是"不做视觉外推"换来简单与稳的代价；
* 你按下的**时刻**误差（而不是位置）会成为整首歌的全局偏移。程序给一个 `offset_ms`
  旋钮：打完看结算页 FAST/SLOW 调一个数即可（一局一跑，人本来就在，不需要造自动闭环）。
