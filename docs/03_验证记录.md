# 验证记录（可复现）

> English abstract: every number this project relies on is either read from the game's data or
> verified by a script that prints residuals. Nothing here depends on a human looking at a picture.

## 1. 几何：模型 vs 实机

材料：**设备上抓的 2510×1156 无损 PNG 截图**，脚本自动筛出 31 张整屏演奏画面。

| 量 | 模型 | 实测 | 残差 |
|---|---|---|---|
| 车道线间距 | 137.5 px | 中位 136.0 px（散布 −3.0 ~ +4.0） | **−1.1%** |
| 最外侧车道线 | x = 430 | x = 440 | +10 px（最外侧是 `out_side_line` 装饰线，本来就画在轨道外一点） |
| 判定线 | 屏高 79.26% | 两条紫线在 75.4% 与 83.0% —— 模型正落在两者正中 | ✓ |
| 按屏宽那一套（对照） | 168.3 px | — | 差 24%，已排除 |

判定线的三条独立来源互相印证：

1. 游戏代码常量（`judgementScreenBottomPosition = 2.24`，平面半高 ±5.4）→ 79.259%；
2. 场景里真实摆放的判定节点（`LiveGameCamera/screen_root/judgement_positions/*`）→ y = −3.160；
3. 用场景里的相机参数正投影计算 → 79.11%。

## 2. 旧版本错在哪（这就是为什么要重做）

| | 旧实现 | 真值 | 后果 |
|---|---|---|---|
| 判定线 y | 83.04%（取了下面那条装饰紫线） | 79.26% | 偏低 44 px |
| 每格宽度 | 71.7 px | 68.8 px | 偏宽 5.5% |
| 最外侧格落点 | 393 px | 430 px | **偏 37 px —— 掉到最外侧车道命中区之外** |

而且旧实现"验证通过"是**结构性**的：它量的是"看起来像边界的那条线"，
校验样本只有一个音符、还在场地中间，误差预算与待测量同量级 —— 于是每次都报 OK。

## 3. 复现方法

```powershell
# A) 拿一批整屏演奏画面截图核对几何（不需要手机）
python tools\verify_geometry.py <截图目录> --limit 8
# 或者：把截图文件夹直接拖到 谛听.exe 上

# B) 重导游戏场景并逐条核对常数（游戏更新后用）
python tools\reexport_scene.py --nnnotes-config <nnnotes.toml> --out <导出目录>
```

判定标准是数字：间距残差中位在 ±2% 以内算通过。

## 4. 便携包的环境验证（"没有 Python 的电脑也能用"）

1. 扫描包内 47 个 PE 文件的导入表：依赖的非系统 DLL 只有 Windows 自带的那些；
   `python311.dll`、`VCRUNTIME140.dll`、`VCRUNTIME140_1.dll` 已随包，
   OpenCV 为静态链接、**不需要** msvcp140。
2. 拷到中性目录，把 `PATH` 只留 `C:\Windows\system32`、清空所有 `PYTHON*` 变量后运行
   `谛听.exe --check` → 退出码 0，各项全过（含"试建虚拟触摸屏"）。
3. 从 zip 解压到全新目录再跑一遍 → 正常启动、自检通过。
